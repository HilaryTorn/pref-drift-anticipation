# SFT Training Data

This directory is for real supervised fine-tuning data, not elicitation
stimuli. The files in `data/source/coding_training_stimuli_v2.json` describe
training options to the model during preference and anticipation elicitations;
they are not a training corpus.

Training data is stored as JSONL. Each line is one chat-style supervised
example:

```json
{
  "id": "coding.write.python.magicoder_pool_00001",
  "intervention_id": "coding.write.python",
  "task": "write",
  "language_id": "python",
  "messages": [
    {"role": "user", "content": "Write a Python function ..."},
    {"role": "assistant", "content": "def ..."}
  ],
  "source": "dataset-name-or-internal-generation-run",
  "license": "license-name",
  "split": "pool"
}
```

Required rules:

- Every example must have source and license metadata.
- Examples must match the intervention's task and language.
- Candidate pools should not include benchmark test items used for evaluation.
- Training examples must not copy task-preference, training-preference, or
  anticipation prompt text.
- Exact train subsets should be generated from candidate pools with
  `scripts/prepare_sft_dataset.py`, so sample count and seed are reproducible.
- Prepared datasets can then be trained with `scripts/train_sft_lora.py`, which
  uses TRL `SFTTrainer` plus PEFT `LoraConfig` and writes a training manifest.

The initial coding SFT scope follows the one-axis pilot — the language axis, with the task held fixed at `write`:

- `coding.write.python`
- `coding.write.cpp`
- `coding.write.java`
- `coding.write.rust`

Debug and explain are **evaluation/spillover targets, not SFT interventions**. Magicoder is a program-writing corpus: it contains no debugging or explanation training data, so those interventions could never be run, and a forecast about them could never be scored against a real drift. Keeping them as targets is what lets a write-only intervention be measured for task spillover. (Translate is not a target either — it was dropped from the battery entirely.)

## How the Pools Were Built

All four arms' `pool.jsonl` (512 examples) and `validation.jsonl` (64 examples) were generated by `scripts/build_sft_pools.py` from `data/training/coding/magicoder_balanced.jsonl` (the balanced Magicoder-OSS-Instruct-75K subset, 4,565 rows per language), with seed 42. Rows are filtered before sampling: empty problems/solutions are dropped; the solution's code-fence tag must match the arm's language (Magicoder's `lang` labels are noisy — ~22% of cpp, ~12% of rust, ~7.5% of java rows are fenced in another language); rendered length is capped at 6,000 chars to fit the spec's 2,048-token `max_seq_length`; duplicates are removed by normalized problem text; and any row containing elicitation/preference stimulus wording is excluded. Pool and validation are disjoint samples from one draw, so they never overlap. Run `scripts/validate_sft_data.py --require-data` after any rebuild.

## Training a LoRA Adapter

After preparing a dataset directory with `train.jsonl` and `validation.jsonl`,
run:

```bash
python3 scripts/train_sft_lora.py \
  --spec_path data/training_specs/coding_axis_sft.json \
  --intervention_id coding.write.python \
  --dataset_dir results/sft_datasets/coding.write.python_n64_seed42 \
  --output_dir results/sft_runs/coding.write.python_n64_seed42
```

By default the trainer uses assistant-only masking and bf16 precision from the
AWS-oriented spec. Recent TRL versions no longer ship the old completion-only
collator, so the runner falls back to a local response-template collator when
needed. The base model also defaults from the SFT spec. Use `--no-bf16` for
local hardware that cannot run bfloat16. For reproducible training installs, use
`uv sync` or `pip install -r requirements-sft.txt`, not the loose scoring
`requirements.txt`. Baseline and post-training elicitation must use the same
base model as this SFT run for drift estimates to be interpretable. To push the
resulting LoRA adapter to Hugging Face, add:

```bash
  --hub_repo_id <org-or-user>/<repo-name> --hub_private
```

The push path uses a trainer callback. It pushes at the end of training by
default; add `--push_on_save` to also upload each intermediate `checkpoint-N/`
folder for drift-trajectory rescoring. Set
`HUGGINGFACE_HUB_TOKEN` or `HF_TOKEN` in the environment before pushing.
